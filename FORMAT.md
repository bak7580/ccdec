`ccdec/reader.py` + `ccdec/model.py`, тесты — `tests/`. Разделы 3–7 проверены на трёх
образцах: каждый блок разобран ровно до последнего байта. Раздел 10 (`.cap`) пока описан
только по исходникам.

## 0. Источники и обозначения

**Исходники:** `github.com/aolko/construct`, ветка `master` — зеркало SVN SourceForge,
ревизия **r321** от 2012-02-05 (`.svn/entries`). В `IDE/StdAfx.h`:
`CONSTRUCT_VERSION_ID 10200`, `CONSTRUCT_VERSION_STRING "Classic r2"`.
Это единственный снимок: истории ревизий в зеркале нет.

**Образец:** пара из самих исходников — `IDE/Tools/Mesh Editor/Mesh Editor.exe`
(2 941 440 байт, PE timestamp 1251065644 = август 2009) и `Mesh Editor.cap` (230 866 байт).
Образец старше исходников примерно на 2,5 года — это полезно: видно, что меняется между версиями.

Метки у фактов:

- **[S: файл :: функция]** — прочитано в исходниках r321.
- **[E]** — проверено на образце `Mesh Editor.exe` / `.cap` (разбор байтов, без запуска).
- **[S+E]** — и то, и другое совпало.
- **[П]** — предположение, не проверено.

Пути исходников даны относительно корня репозитория.

## 1. Контейнер: где лежат данные проекта в .exe

**Данные лежат в секции ресурсов PE (`.rsrc`), а не в оверлее.** Сжатия, шифрования
и обфускации нет. Контрольных сумм и общего заголовка тоже нет.

- Редактор копирует готовый рантайм (`Data\DX9.exe`, `Data\App.exe`, с суффиксом `_s`
  для Python, `_p`/`_pd` для превью) и дописывает ресурсы через
  `BeginUpdateResource` / `UpdateResource` / `EndUpdateResource`.
  [S: `IDE/Structure/Export/Export.cpp` :: `CExport::ExportToEXE`, `CExport::DoExport`]
- Рантайм читает их через `FindResource` / `LoadResource`.
  [S: `Runtime/CRuntime_init.cpp` :: `OpenResourceBinary`, `CRuntime::Initialise`]
- У образца оверлея нет (конец последней секции = размер файла), все блоки найдены в `.rsrc`. [E]

### 1.1. Таблица ресурсов

| Тип ресурса | Имя/ID | Содержимое | Источник |
|---|---|---|---|
| `APPBLOCK` | 997 | настройки приложения, глобальные переменные, управление | [S+E] `CExport::GenerateApplicationData` ↔ `CCapReader::ReadAppProperties` |
| `LEVELBLOCK` | 998 | типы объектов, behaviors, traits, families, контейнеры, layouts, layers, экземпляры, анимации | [S+E] `CExport::GenerateLayout` ↔ `CCapReader::ReadFrameData` |
| `EVENTBLOCK` | 999 | имена event sheets + дерево событий на каждый layout | [S+E] `CExport::GenerateEvents` ↔ `CCapReader::ReadEventList` |
| `IMAGEBLOCK` | 995 | все изображения (PNG или BMP) + хотспоты, action points, маски коллизий | [S+E] `CExport::GenerateImages` ↔ `CCapReader::ReadImageData` |
| `HLSL` | 994 | скомпилированные эффекты и их привязка к объектам/слоям, transitions | [S+E] `CExport::GenerateHLSL` ↔ `CCapReader::ReadHLSLData` |
| `MENUBLOCK` | 993 | всегда `int 0` (меню отключены в коде) | [S+E] `CExport::ExportResources`; у образца 4 байта `00 00 00 00` |
| `PYTHONLIBS` | 992 | ZIP с модулями стандартной библиотеки Python (только если включён Python) | [S] `CExport::GeneratePython` ↔ `CCapReader::ReadPythonResources` |
| `DLLBLOCK` | 1000…1000+N−1 | файлы плагинов и behaviors (`.csx` = обычные PE DLL) целиком | [S+E] `CExport::DoExport` ↔ `CRuntime::UnpackPlugins` |
| `FILES` | 1…M | пользовательские файлы-ресурсы, сырые байты, **без имён** | [S] `CExport::ExportResources` |
| `DEPENDENCIES` | имя файла в ВЕРХНЕМ регистре | DLL-зависимости плагинов | [S] `CExport::ExportResources` ↔ `CRuntime::UnpackDependencies` |
| `RT_STRING` (6) | блок 1, строка 1 | число N плагинов+behaviors десятичной строкой | [S+E] у образца `"13"`, `DLLBLOCK` 1000–1012 |
| `RT_ICON` (3) | 1 | иконка 32×32 (ICO без 22-байтного заголовка) | [S+E] |
| `RT_GROUP_ICON` (14) | `MAINICON` | описатель иконки | [S+E] |

Порядок `DLLBLOCK`: сначала плагины в порядке первого появления типа объекта,
затем behaviors. Индекс плагина в данных = `ID − 1000`.
[S: `CExport::GenerateLayout` (`dllList`, `MvtLookup`), `CExport::DoExport`]

Остальные ресурсы образца (`RT_MENU` 131–136, `RT_DIALOG` 129–131, `RT_MANIFEST`)
принадлежат шаблону рантайма, а не проекту. [E]

Формат строки-счётчика: редактор пишет блок `RT_STRING` нестандартно — в блок с ID = d
кладёт пустую строку в слот 0 и текст в слот 1 (`u16 длина` + UTF-16LE).
[S: `Export.cpp` :: `AllocStringResourceFormat(text, 1, …)`] [E: `00 00 02 00 '1' '3'`]

Проверки целостности, которые делает `container.py` (общей контрольной суммы в формате нет,
поэтому сверяется то, что следует из кода экспорта):
обязательные блоки присутствуют; число `DLLBLOCK` равно строке-счётчику; ID `DLLBLOCK`
идут подряд от 1000, `FILES` — от 1; `MENUBLOCK` равен четырём нулевым байтам;
оверлея нет. Нарушения попадают в предупреждения, а не роняют разбор.

### 1.2. Превью-сборки

В режиме превью (`Temp.exe` в `%APPDATA%\Scirra`) вместо `DLLBLOCK` пишутся строки
`RT_STRING` 1000+ с **именами** файлов плагинов, зависимости не встраиваются.
[S: `CExport::DoExport`, ветка `previewMode`]. Такой файл не самодостаточен;
инструмент должен распознавать его и сообщать об этом.

### 1.3. Установщик

Если при экспорте выбран установщик, готовый .exe кладётся внутрь другого .exe
ресурсом `RUNTIME`/131. [S: `IDE/Structure/Export/Export - Installer.cpp`]
Формат остального содержимого установщика не изучен (см. открытые вопросы).

## 2. Примитивы сериализации блоков (класс `bin`)

[S: `Common/bin.h`] Всё little-endian, без выравнивания.

| Тип C++ | Байт | Замечание |
|---|---|---|
| `bool`, `char`, `BYTE` | 1 | |
| `int`, `long`, `unsigned`, `size_t`, `float`, `COLORREF` | 4 | рантайм 32-битный |
| `__int64`, `double` | 8 | |
| `CString` | 4 + len | `int len` (включая завершающий `\0`), затем `len` байт. Кодировка — ANSI-кодовая страница машины автора [П: имя кодировки нигде не записано] |
| `bin` (вложенный блок) | 4 + size | `int size`, затем байты |

Ловушка, на которой я ошибся при проверке: размер поля определяется **объявленным типом
члена класса**, а не тем, как его читает рантайм. Например, `show_menu` и `fps_in_caption`
объявлены как `int` (4 байта), хотя по смыслу булевы. [S: `IDE/Structure/CApplication.h`] [E]

Версионного поля, сигнатуры или длины ни у одного блока **нет**. Блок считается
разобранным верно, если чтение закончилось ровно на его последнем байте.

## 4. LEVELBLOCK (998)

[S: `IDE/Structure/Export/Export - Layout.cpp` :: `CExport::GenerateLayout`, `ExportAnimations`
↔ `Runtime/CapReader.cpp` :: `CCapReader::ReadFrameData`, `ParseAnimations`]

Разделы идут подряд:

1. **Типы объектов**: `int n`; для каждого — `int oid` (плотный индекс 0…n−1),
   `CString имя`, `int индекс плагина`, `char global`, `int destroyWhen`,
   `int k` + k × (`CString имя переменной`, `int тип`), 16 байт нулей, `BYTE флаг`.
   Если флаг = 1, следует **таблица ACE плагина**: три списка (actions, conditions,
   expressions), каждый — `int m` + m × (`CString scriptName`, `int числоПараметров`).
   Флаг = 1 стоит у первого типа каждого плагина. [S+E: на образце разобрано 27 типов]
2. **Behaviors**: `int n`; для каждого — `int oid владельца`, `int индекс DLL`,
   `int порядковый номер у объекта`, `CString имя`, `int размер` + сырые данные свойств,
   `BYTE флаг` (+ таблица ACE, как выше). [S+E: 2 behaviors — `DragDrop`, `SelectionBox`]
3. **Traits (атрибуты)**: `int n`; n × (`CString имя`, `int k`, k × `int oid`).
4. **Families**: `int n`; n × (`CString имя`, `int k`, k × `int oid`,
   `int v`, v × (`CString имя переменной`, `int тип`)). Экспортируются только используемые.
5. **Контейнеры**: `int n`; n × (`int k`, k × `int oid`).
6. **Layouts**: `int n`; для каждого:
   - `int ширина`, `int высота`, `CString имя`, `int цвет`, `bool unbounded scrolling`,
     `bool application_background`;
   - ключи layout: `int n` + n × (`CString`, `int тип`, `int` либо `CString`);
   - **слои**: `int n`; для каждого — `int id`, `CString имя`, `BYTE тип`, `int цвет-фильтр`,
     `float opacity`, `float угол`, 4 × `float` прокрутка, 4 × `float` зум,
     `char clearBack`, `int backColor`, `bool forceOwnTexture`, `int sampler`,
     `bool enable3d`, `bool clearDepthBuffer`, затем **экземпляры**;
   - **экземпляр**: `int (мусор, игнорируется)`, `int x, y, w, h`, `float угол`,
     `int фильтр`, `int oid`, `int instanceID`, `int oid` (повтор),
     `int k` + k × `CString` начальные значения приватных переменных,
     `int размер` + **сырые данные свойств плагина**;
   - `int n` + n × `int` — список ID изображений, используемых layout;
   - `int texture_loading`.
7. **Анимации** (рекурсивное дерево): `int n`; для каждой — `int id`, `CString имя`,
   `int tag`, `float скорость`, `BYTE isAngle`, `float угол`, `int repeat` (−1 = вечно),
   `int repeatTo`, `int pingpong`, `int кадров` + кадры (`float время`, `int id изображения`),
   затем вложенный список под-анимаций.

Особенность порядка слоёв: редактор переносит первый слой в конец списка
(«non-layout layer»). [S: `GenerateLayout`, блок `rearrange`]

Все семь разделов разобраны до конца блока на трёх образцах. [E1][E2][E3]

### 4.1. Данные свойств плагина (`eData`)

Это вывод функции плагина `ETSerialize` — формат свой у каждого плагина, обычно начинается
с `int Version`. [S: `GenerateLayout`; пример — `Plugins/Sprite/Serialization.cpp` ::
`EditExt::Serialize`, версия 5; чтение в рантайме — `Plugins/Sprite/Runtime.cpp`]

**Ключевой факт для Level 3:** `.cap` хранит **тот же самый блок** — редактор при сохранении
вызывает тот же `ETSerialize` и пишет `int размер` + байты.
[S: `IDE/Structure/CObject.cpp` :: `CObj::Serialize`]
Проверено на паре [E2]: из 70 блоков свойств экземпляров 67 побайтно найдены в `.cap`
(вместе с префиксом длины). Оставшиеся 3 — спрайты игрока, отличаются только 4 байтами
id корневой анимации: в `.cap` это 399/405/411, а в `.exe` максимальный id анимации 383.
То есть `.cap` сохранён **позже** экспорта, пара не строго синхронна.
Значит, для пересборки `.cap` данные плагина можно переносить как есть, не понимая их.
Расшифровка нужна только для читаемого JSON (Level 2).

## 5. EVENTBLOCK (999)

[S: `IDE/Structure/Export/Export_Events.cpp` ↔ `Runtime/CapReader.cpp` :: `ReadEventList`,
`ParseEvent`, `ParseEventGroup`, `GetConditions`, `GetActions`, `GetParams`]

Заголовок: `int n` + n × `CString` — имена event sheets; затем `int числоСписков`
(= числу layouts), затем по одному списку событий на layout.

Маркеры — один байт [S: `Runtime/CapReader.h`, `IDE/Structure.h`]:

| Байт | Маркер | Байт | Маркер |
|---|---|---|---|
| 1 | BEGINEVENTLIST | 9 | ENDACTION |
| 2 | BEGINEVENT | 10 | ENDACTIONS |
| 3 | BEGINCONDITIONS | 13 | ENDEVENT |
| 4 | BEGINCONDITION | 14 | ENDEVENTLIST |
| 5 | ENDCONDITION | 15 | BEGINGROUP |
| 6 | ENDCONDITIONS | 16 | ENDGROUP |
| 7 | BEGINACTIONS | 11, 12 | BEGINPARAM / ENDPARAM — объявлены, не используются |
| 8 | BEGINACTION | | |

Грамматика:

```
список   := 1 { событие | группа } 14
событие  := 2 int:номерСтроки int:индексЛиста
            3 { условие } 6
            7 { действие } 10
            { событие | группа }        ; под-события
            13
группа   := 15 BYTE:активна CString:имя { событие | группа } 16
условие  := 4 int:oid int:cndID BYTE:negated int:movID int:nParams { параметр } 5
действие := 8 int:oid int:actID int:movID int:nParams { параметр } 9
параметр := int:nTokens { токен }
токен    := int:тип [ данные ]
```

- `oid = −1` — системный объект. `movID ≥ 0` — номер behavior у объекта; `movID ≤ −2` —
  эффект (индекс `−2 − movID`); `−1` — сам объект.
  [S: `CExport::ConvertMID`, `CCapReader::TranslateAction`]
- Данные токена: `T_INTEGER` → `__int64`; `T_FLOAT` → `double`;
  `T_STRINGLITERAL`, `T_IDENTIFIER`, `T_VARIABLENAME` → `CString`; остальные — без данных.
  [S: `CExport::ExportParameter` ↔ `CCapReader::GetParams`]
- Нумерация типов токенов — перечисление `ExpToken`, с нуля: `T_NULL, T_ANY_BINARY_OPERATOR,
  T_ANY_FUNCTION, T_ANY_VALUE, T_INTEGER(4), T_FLOAT(5), T_STRINGLITERAL(6), T_IDENTIFIER(7),
  T_ARRAY(8), T_VARIABLENAME(9), T_LEFTBRACKET(10), T_RIGHTBRACKET, T_COMMA, T_DOT,
  T_LEFTCURLY, T_RIGHTCURLY, T_AT, T_ADD(17), T_SUBTRACT, T_MULTIPLY, T_DIVIDE, T_MOD,
  T_POWER, T_SIN, T_COS, T_TAN, T_SQRT, T_FUNC_STR, T_FUNC_INT, T_FUNC_FLOAT, T_EQUAL(30),
  T_LESS, T_GREATER, T_LESSEQUAL, T_GREATEREQUAL, T_NOTEQUAL, T_CONDITIONAL, T_COLON,
  T_AND, T_OR, T_ASIN(40) … T_LEN(51)`. [S: `Runtime/CExpression.h`]
  Перечисление в редакторе (`IDE/Editors/Expressions/CExpression.h`) нужно сверить
  с рантаймовым целиком — сверена только первая строка.

Дерево разобрано полностью: [E1] — 95 событий, 30 групп, 84 условия, 124 действия;
[E2] — 8 событий; [E3] — 75 списков. Неизвестных типов токенов не встретилось.

### 5.1. Что редактор делает с событиями перед записью (необратимые преобразования)

[S: `CExport::AddEvent`, `ExportBlock::ProcessEventsTriggers`, `ExportEvent::ProcessWait`,
`ExportScript::Export`, `CExport::ExportParameter`]

1. **Include разворачивается на месте.** Отдельных листов в данных нет: на каждый layout
   один плоский список. У события остаётся `индексЛиста`, но это номер в порядке первого
   использования, а не позиция в списке имён (в коде есть комментарий автора, что они
   могут не совпадать).
2. **Отключённые события, условия и действия не экспортируются.** Комментарии — тоже.
3. **Триггеры выносятся на верхний уровень**: событие с триггером клонируется, родительские
   условия копируются в обёртку.
4. **Условия и действия плагина Wait переписываются** в пары «активировать / по активации».
5. **Python-скрипт в листе** превращается в системное действие №45 со строкой-параметром.
6. Параметры хранятся потоком токенов, исходный текст выражения не сохраняется.
   Цвет превращается в целое, ссылка на объект — в `oid`, приватная переменная —
   в `_varindex(индекс, oid)`, глобальная — в индекс, файл-ресурс — в номер.
7. Типы параметров редактора (`EDITORPARAM_*`: строка, цвет, клавиша, слой и т. д.)
   не записываются.

## 9. Версии рантайма и как их различать

Номера версии в блоках данных **нет**. Различия приходится определять косвенно.

Установленный факт: APPBLOCK образца (сборка 2009 г.) отличается от r321 ровно одним
полем — отсутствует `eye_distance`. [E] В `.cap` это поле появилось в `CApplication` v18;
`.cap` образца имеет v17. [S+E]

План распознавания (подлежит проверке на реальных файлах):

1. PE timestamp рантайма и хэши встроенных `.csx` → грубая привязка к сборке.
2. Набор именованных «профилей раскладки» (r2/r321; «до eye_distance»; далее по мере находок).
   Профиль подходит, если строгий разбор дошёл ровно до конца **всех** блоков.
3. Если не подошёл ни один — блок сохраняется сырым, в отчёте указывается смещение сбоя.

Второе найденное отличие: у слоёв в LEVELBLOCK сборки 2009 г. нет последнего поля
`bool clearDepthBuffer` (хвост слоя 11 байт вместо 12). [E1]

Реализованные профили (`reader.PROFILES`):

| Профиль | APPBLOCK `eye_distance` | Слой `clearDepthBuffer` | Подтверждён на |
|---|---|---|---|
| `r2` | есть | есть | [E2], [E3] (сборки 2011 г.), исходники r321 |
| `0.99-2009` | нет | нет | [E1] |

Профиль подбирается для каждого блока отдельно. EVENTBLOCK, IMAGEBLOCK и HLSL у всех трёх
образцов имеют одинаковую раскладку. Какие ещё поля менялись в более ранних 0.9x —
неизвестно, см. открытые вопросы.

## 10. Формат .cap

[S: `IDE/Structure/SaveLoad.cpp` :: `CMainFrame::DoSave`, `DoLoad`;
`IDE/Structure/capplication.cpp` :: `CApplication::Serialize`;
`IDE/Structure/ObjectFunctions.cpp` :: `SerializeClassHeader`, `SerializeClassPadding`]

- Заголовок: 13 байт `"Construct1.7\0"`. [S+E]
- Дальше — поток **MFC `CArchive`**, а не `bin`. Отличие в строках: `CString` пишется
  с однобайтовой длиной (и эскейпами `0xFF` для длинных/юникодных строк), без `\0`. [S+E:
  в образце `0C "CApplication"`, `0F "Mesh Editor 1.0"`, `06 "Scirra"`]
- Каждый класс начинается с `CString имяКласса` + `int версия`; при несовпадении имени
  редактор отказывается грузить файл. Многие классы заканчиваются «набивкой» из пустых
  строк и нулей (`SerializeClassPadding`).
- Корень — `CApplication`. Версии классов в r321:

| Класс | Версия | Класс | Версия |
|---|---|---|---|
| CApplication | 18 | CImageResource | 2 |
| CLayout | 5 | CBinaryResource | 2 |
| CLayer | 7 | CEditorEvent | 2 |
| CObj | 3 | CEditorCondition | 2 |
| CObjType | 4 | CEditorAction | 2 |
| CAnimation | 3 | CEditorParam | 1 |
| CFamily | 1 | CEffect | 1 |

- `CApplication::Serialize` читает старые версии (ветки `Version >= 3 … 18`), то есть
  **r2 открывает `.cap`, сохранённые старыми редакторами**, начиная с формата
  `Construct1.7`. Файл новее редактора отвергается по `created_with > CONSTRUCT_VERSION_ID`.
- Порядок разделов `CApplication` (v18): свойства приложения → список использованных
  плагинов (имя + имя файла) → layouts → анимации → изображения (PNG внутри файла) →
  файлы / звуки / музыка → иконки → меню → типы объектов → traits → families →
  глобальные переменные → контейнеры → системный объект → transitions → event sheets →
  управление → ключи → список модулей Python → папки объектов → набивка 30 строк + 20 int.
- **Звуки, музыка и файлы в `.cap` хранятся только как путь на диске**, без содержимого
  (`CBinaryResource`: имя, тип, путь, id). [S: `IDE/Structure/Resources.cpp`]

Пополевые описания всех классов — в `ccdec/cap_format.py`: каждая функция там соответствует
одному `Serialize` из исходников (имя указано в docstring) и служит одновременно читателем и
писателем. Оба эталонных `.cap` (v17 и v18) читаются до конца и записываются обратно
**байт в байт**. [E1][E2]

## 13. Метаданные условий, действий и выражений (Фаза 3)

### 13.1. Номера ACE у плагинов

- Первый вызов `EditAce` заполняет 255 пустых слотов; собственные ACE плагина добавляются в конец,
  то есть получают номера **255, 256, …**; общие ACE (`Common/CommonAceTable.hpp`, макросы `ADD*_AT`)
  имеют явные номера < 255. [S: `IDE/Construct.cpp` :: `MicroAceTool::EditAce`; рантайм —
  `Runtime/CRuntime_init.cpp` :: `MicroAceTool::RunAce`]
- Таблица ACE в LEVELBLOCK — это весь вектор, вместе с пустыми слотами: длина = 255 + число своих
  ACE. Номер условия/действия в EVENTBLOCK = индекс в этой таблице. [S: `GenerateLayout`]
  [E1][E2][E3: у всех плагинов длины таблиц ≥ 255, у плагинов без общих ACE первое имя на 255]
- Отображаемый текст, имена и **типы параметров** в `.exe` не попадают — только `scriptName` и число
  параметров. Они берутся из исходников генератором `tools/gen_aces.py` → `ccdec/data/aces.json`
  и подставляются только если имя и число параметров совпали с таблицей из `.exe` (`ccdec/aces.py`).
  Совпадение на образцах: Sprite, Text, Tiled Background, Box, Mouse & keyboard, Edit, Function,
  Line, Drag&Drop, Car, RTS — 100 %; Platform 97 %; XAudio2 67 %. Button, CommonDialog, File, MOD,
  Imagelist, SelectionBox, MouseMov — исходников в репозитории нет.
- Ключи Mouse & keyboard — это **индекс в списке `keyTable[]`** плагина (combo), а не VK-код.
  [S: `Plugins/Mouse & keyboard/Main.cpp`] Генератор восстанавливает список.

### 13.2. System

- Таблиц ACE у System в `.exe` нет вообще. Источник — `IDE/Structure/SystemObject.cpp`:
  `switch` по номеру в `GetSystemCondition` / `GetSystemAction`, строки через
  `GetString(раздел, ключ)` из `IDE/Languages/English (UK)/<раздел>.txt`. Генератор разбирает 34
  условия и 50 действий. Проверить их по `.exe` нельзя; на образцах все встреченные номера System
  нашлись в базе. [S][E1][E2][E3]
- Действие 45 «Run Script» — Python-скрипт листа (`ExportScript::Export`), строка в параметре.
- Условия 17 (Else) и 18 (OR) рантайм обрабатывает особо. [S: `CapReader.cpp`]

### 13.3. Выражения

- `&` и `and` — один токен `T_AND` (так же `|`/`or`, `!=`/`<>`, `floor`→`T_FUNC_INT`,
  `log`→`T_LN`). Восстановить, как было написано, нельзя; `ccdec` пишет `&`, `or`, `<>`, `int`, `ln`.
  [S: `IDE/Editors/Expressions/CExpression.cpp` :: `CheckForKeywords`, `ParseUserString`]
- Сокращение `.X` («своё X») в `.exe` превращается в `Объект.X`. [E1: в `.cap` у таких токенов
  пустая строка идентификатора, в `.exe` — имя объекта]
- Параметры-объекты, приватные и глобальные переменные, файлы, цвета, комбо в `.exe` хранятся
  числами (`ObjTypeIDCnvt`, `_varindex(i, oid)`, индекс переменной, индекс файла, COLORREF, индекс
  варианта). Типы параметров известны только из базы ACE, поэтому для плагинов без исходников
  эти числа остаются числами. [S: `CExport::ExportParameter`]
- Пространство runtime-идентификаторов объектов: `[0, nt)` типы, затем behaviors (`Тип[Behavior]`),
  затем атрибуты, затем families. [S: `CExport::ObjTypeIDCnvt`, `CCapReader::ReadFrameData`]

### 13.4. Что показала сверка с `.cap`

- **Изображения** в `.exe` и `.cap` побайтно одинаковые (PNG не перекодируется заново). [E1: 7 из 7;
  E2: все 6 сохранившихся различных изображений] Сравнивать можно по хэшу, по пикселям не нужно.
- `.cap` хранит только изображения, на которые ссылаются объекты (`images_to_save`), а `.exe` —
  **все** изображения проекта, включая деревья анимаций удалённых объектов. [S: `GenerateImages`,
  `ExportAnimations`; E2: 35 таких деревьев, E3: 1] `ccdec` кладёт их в `images/_orphaned_animation_*`.
- Анимации привязаны к объекту только через свойства экземпляра Sprite (`animation_root`). У
  экземпляров одного типа корень может различаться (вставка с клонированием). [E2]
- `.cap` хранит параметры событий **токенами редактора** (`CEditorParam`: тип параметра, токены с
  пробелами, `T_COLOR`, ссылки на объекты по edit-time id). [S: `IDE/Editors/EditorParam.cpp`]
  Все параметры типов «значение/строка/слой/массив», восстановленные из `.exe`, нашлись среди
  `CEditorParam` эталонного `.cap` (после удаления пробелов и с учётом `.X`). [E1: 83 из 83; E2: 3 из 3]
  Полное сравнение деревьев событий (порядок, группы, вложенность) требует читателя `.cap` — Фаза 4.
- Файлы `FILES`: MP3 бывают без ID3 и с ~400 нулевыми байтами в начале. [E3]
- Свойства плагинов расшифровываются для Sprite (v5), Text (v2), Tiled Background (v2), Panel (v2),
  Platform (v5) — на всех образцах блоки прочитаны до конца. [S: `EditExt::Serialize` каждого
  плагина][E1][E2][E3]

## 14. Level 3: пересборка `.cap` (Фаза 4)

### 14.1. Что подтверждено о формате `.cap`

- `cap_format.py` читает и побайтно воспроизводит оба эталона: `Mesh Editor.cap` (CApplication v17,
  `created_with` 9900) и `.cap` образца A (v18, `created_with` 10102). [E1][E2]
- Типы полей: `bool` — 1 байт, `BOOL`/`int`/`long`/`size_t` — 4 байта, `CRect` — 16 байт, `float` — 4.
  [S: объявления в заголовках IDE][E1][E2 — иначе разбор не дошёл бы до конца файла]
- `CObj` хранит поле-указатель редактора (`peditInfo`, мусор), `CEditorEvent` — мусор в `m_BreakPoint`. [E2]
- Имя плагина в `.cap` — это **отображаемое имя** (`extName`), а не имя файла. Оно лежит в строковом
  ресурсе 1 (`OBJ_NAME`) самой DLL плагина, в том числе рантаймовой из `DLLBLOCK`.
  [S: `IDE/Construct.cpp` :: `LoadString(…, OBJ_NAME, …)`][E1][E2: имена из DLL совпали со списком
  плагинов в `.cap`] Работает и для сторонних плагинов.
- Строки и элементы событий с `Space <= 0` редактор удаляет при отрисовке.
  [S: `chronoeventeditor.cpp`, проверки `m_Anim.Space <= 0`] `ccdec` пишет положительные значения.
- В `CApplication::Serialize` загрузчик читает `globalKeys` как «старый» формат для всех версий,
  кроме 5, а писатель всегда пишет «новый». Непустую коллекцию редактор сам не прочитает.
  [S] `ccdec` глобальные ключи не пишет.
- `comboIndex` элемента управления — индекс VK-кода в `controlTable[]`.
  [S: `IDE/Bars/AppProperties.cpp`][E2: все 9 элементов совпали]

### 14.2. Параметры событий в `.cap`

- Параметр — список токенов **редакторского** токенизатора (`ParseUserString(editorMode = true)`
  + `ProcessEdittimeExpressionInformation`): пробелы — отдельные токены `T_WHITESPACE` (52), цвет —
  `T_COLOR` (53), у имён объектов проставлены владелец и подтип, у переменных — id.
- `ccdec/cap_tokens.py` — перенос этих двух функций. Проверка: для каждого параметра-выражения из
  эталонов исходный текст токенизируется заново и сравнивается со всеми полями сохранённых
  токенов — **208 из 208 совпали** (199 в [E1], 9 в [E2]).
- Особенность редакторского режима: `-` после пробела сохраняется как токен `T_INTEGER` с текстом `-`. [E1]
- Параметры «объект», «приватная/глобальная переменная», «комбо», «цвет» хранятся одним числом:
  id типа объекта, id переменной, индекс варианта (а текст варианта — в поле `reserved`), COLORREF. [E1]

### 14.3. Как собирается `.cap` из `.exe`

| Данные | Источник | Замечание |
|---|---|---|
| Свойства объектов и behaviors | блоки из `.exe` как есть | те же байты, что в `.cap` |
| Изображения, анимации | `.exe` | только используемые объектами; имена `ObjectImage<id>` |
| id экземпляров | `.exe` | это исходные id редактора |
| id типов объектов, behaviors, эффектов, families | назначаются заново | в `.exe` их нет |
| id приватных и глобальных переменных | порядковый номер | |
| Иконки типов объектов | миниатюра первого кадра | исходные иконки не экспортируются |
| Происхождение (`originX/Y`) объекта | hotspot первого кадра (Sprite), иначе 0 | [П] для прочих плагинов |
| Флаги `draw`/`show_angles` объекта | таблица по плагину из эталонов | для неизвестных плагинов 1/1 [П] |
| Цвет layout | RGB из `.exe` + старший байт `0xFF` | экспортёр отбрасывает старший байт |
| Листы событий | по одному на layout | include развёрнуты, см. §5.1 |
| Триггеры в группах | возвращаются в свои группы | см. ниже |
| Файлы-ресурсы | путь к извлечённому файлу | `.cap` и в оригинале хранит только путь |

**Триггеры.** Экспортёр превращает `Группа{ Событие(триггер, …) }` в верхнеуровневое
`Событие(триггер){ Копия-группы{ Событие(…) } }` в конце списка.
[S: `ExportEvent::ProcessThisEventForTrigger`][E1: 24 таких события] `ccdec` распознаёт эту форму
и возвращает событие в исходную группу — в её конец, так как позиция внутри группы не сохраняется.
Триггеры, вынесенные из под-событий обычных событий, остаются в переписанном виде.

### 14.4. Проверка без редактора

`ccdec/compare.py` приводит дерево `.cap` к канонической форме без id и сравнивает проекты.

- **[E1]** `.cap`, пересобранный из `Mesh Editor.exe`, **эквивалентен** исходному `Mesh Editor.cap`:
  настройки, 27 типов объектов (переменные, behaviors, эффекты, атрибуты), слои, 36 экземпляров,
  анимации и всё дерево событий (71 событие, 6 групп, 368 параметров). Оговорки: порядок
  триггеров внутри группы не сравнивается; свойства Sprite сравниваются по значению, так как
  `.exe` собран более новой версией плагина (блок v5 против v4).
- **[E2]** Для образца A расхождения ограничены тем, что изменено в `.cap` после экспорта:
  три спрайта игрока и их анимации, одно значение Platform, несколько событий. 69 из 70 типов
  объектов совпали полностью.
- **Чего эта проверка не доказывает:** что редактор откроет файл. Значения по умолчанию для
  editor-only полей взяты из эталонов, но их достаточность проверяется только запуском Construct.

### 14.5. Типы параметров для плагинов без исходников

`tools/learn_aces.py` извлекает типы параметров из любых имеющихся `.cap`
(`ccdec/data/aces_learned.json`, ключ — отображаемое имя плагина, вид и номер ACE). Используется
только когда нет исходников и совпадает число параметров. Сейчас база построена по двум эталонам,
поэтому совпадение [E1] по плагинам Button/CommonDialog/File/SelectionBox отчасти круговое: эти
типы взяты из того же `.cap`, с которым идёт сравнение. Для ACE, которых нет в базе, параметры
пишутся как обычные значения — для параметров-объектов это неверно, такие места перечислены в отчёте.

### 14.6. Открытые вопросы Level 3

1. Пересобранный `.cap` образца [E3] (75 layouts) **открывается в Construct Classic r2**:
   видны layouts, объекты с миниатюрами, свойства layout, привязка листов событий (проверено
   вручную, 2026-11-12). Там же проверены редактор событий (тексты условий и действий,
   включая `XAudio2: Play music "file_0036.wav"`) и Preview (игра запускается, звук подключён).
   **Повторный экспорт из r2 выполнен**, `--compare-exe` даёт `equivalent`. Побайтно блоки
   отличаются ожидаемо: путь к `.cap` в APPBLOCK; порядок типов объектов (экспортёр обходит
   хэш-таблицу, поэтому runtime-id перенумерованы — отсюда отличия LEVELBLOCK и EVENTBLOCK при
   том же размере EVENTBLOCK 17087); в IMAGEBLOCK нет одного изображения из анимации без
   владельца; плагины — сборки из поставки r2 и в другом порядке. Все 41 файл `FILES`
   побайтно совпали, 433 типа объектов и 175 из 176 изображений те же.
   Критерий приёмки 3 для [E3] выполнен. Для [E2] и [E1] повторный экспорт не делался.
   Замечание об окружении: редактор — не-юникодная программа. При системной кодовой странице
   1252 он не открывает файлы с кириллицей в пути (молча) и показывает кириллические строки
   проекта кракозябрами, хотя байты в `.cap` верные (cp1251).
2. Families: пересборка написана по исходникам, образцов с families нет.
3. Эффекты слоёв и transitions: образцов нет.
4. `originX/Y` и флаги отображения для плагинов вне таблицы.
5. Группы объектов редактора (`m_bIsGroup`) в `.exe` не сохраняются — объекты пишутся без групп.
